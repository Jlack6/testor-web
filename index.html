How a run works

Open the installed app, replay what is already known, and spend a model call only where a step still needs one.

STAGE 1

Open the app in the Simulator

The suite decides whether to build. A suite set to rebuild builds first. A suite left on the installed app reuses what is already there, and does not silently rebuild. If you run every case with no suite selected, Testor may build when launch fails. Stop during setup cancels the run.

STAGE 2

Turn the case into a plan

Steps are one per line. An accessibility identifier already written on a step, like (id: notes.addButton), becomes a saved control. Lines that start with verify, check, or confirm are not separate model calls. They wait for the single check at the end. Changing a step’s wording drops the controls saved for that line.

STAGE 3

Replay the controls you already have

A step with a saved identifier or label is tapped, typed, or swiped directly. That step does not call the model. The same case gets cheaper every time those controls still match the screen. A coordinate-only tap is not saved, because it will not find the control next time.

STAGE 4

Ask the model only for an empty step

The next run of a step with nothing saved asks the model to do that step, then stores the identifier and label it used. If a saved control is missing, the error is noted and the model does the step. The control that worked replaces the old one. Verify steps are skipped here and left for the final check.

STAGE 5

One check, then the result

After the steps, Testor looks at the screen and reports pass or fail. Screenshots from that check show up in the run activity. A failed case does not stop the rest of a suite. Stop does. If the tool-round limit is on, hitting it ends the run instead of nudging the model to keep going.

A project is a local iOS repo

Add a project from the sidebar. Testor keeps that repo’s cases, runs, and chats together. The status line under the sidebar names the simulator Testor is using, next to Ready.

  • The first time the UI driver starts, it can take a while. Later calls reuse it.
  • Taps prefer an accessibility identifier. The label is the fallback.
  • Setup steps on a suite can run before the cases, when the suite needs the app in a known place.

Prices stay visible

Turn on request prices in Settings. Each model call shows an estimate under that reply, and the composer shows the total for the chat. A chat that has not spent anything shows $0.00. Runs show the same kind of total.

Tool rounds have a limit

One round is one request to the model. Reading the screen, tapping, and typing each use a round. The default stop is 20, and it applies to chats and runs. You can raise it, or turn the limit off and leave a run going until it finishes or you press Stop. When the limit hits, Testor stops and says so.

Test cases and saved controls

A case keeps its steps and the result you expect. Every suite that includes that case stays current, because the steps live on the case, not copied into the suite.

  • Under each step, Testor keeps the identifier or label that worked.
  • A rerun uses those controls and does not call the model.
  • A step with nothing saved asks the model once, then stores what it used.
  • Clear saved controls drops them for the whole case. Editing the words of a step drops just that step’s controls.
  • You can run one case, one suite, or every case.

Runs

History is the list of runs for this project. Open one to see when it started, how long it took, what it cost, and the activity as it happened.

  • Passed and failed cases in a suite stay listed separately.
  • A tool error on one case does not fail the cases that have not run yet.
  • Stop ends the whole run.
  • Activity follows along only while you are already at the bottom. Scrolling up keeps your place.

Screenshots in the activity

When a run takes a screenshot, a small image appears on that activity row. Click it and the shot opens larger. You can move through the other shots from that run. Deleting a run deletes its images too.

Settings

Settings is a page in the main pane, opened from the gear. It is not a small sheet. API keys stay in the Keychain on this Mac.

  • Model. Pick the provider and the model. Save stores the key.
  • Appearance. Blue or Grey. Accent color stays in both.
  • Workspace. Request prices, the context panel, and the tool-round limit. These apply to every project.

Cases, runs, and chats stay on this Mac with the app. The product repo does not receive them unless you ask Testor to write something there.
